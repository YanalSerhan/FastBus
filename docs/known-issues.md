| KI-002 | clang-format output differs between major versions. | A different local clang-format could disagree with CI. | **Mitigated:** clang-format 18.1.8 is pinned in `uv.lock` and used everywhere via `uv run` (CI, CMake, `dev.ps1`, pre-commit). | Bump deliberately with `uv lock --upgrade-package clang-format` + reformat commit. |
| KI-003 | ThreadSanitizer, UBSan, GCC and coverage have no MSVC equivalent, so they cannot run on a Windows-only machine. | Data races / UB are only caught after pushing. | They run in CI (Linux runners) on every push/PR; optional WSL2 for local runs. | KI-004 | Files exempt from the file-length rule: tests, benchmarks, generated code, `src/platform/{windows,posix}`. | Those files can grow large. | Review. | Listed here as exemptions are added. |
| KI-006 | Building inside a OneDrive-synced folder. | Slow builds, `LNK1104` file-lock errors, MAX_PATH failures in deep `_deps` paths. | Clone to a short local path (e.g. `C:\dev\FastBus`), `git config --global core.longpaths true`. `dev.ps1 doctor` warns. | Documentation only. |
| KI-007 | MSVC AddressSanitizer on Visual Studio 2022 **17.4** (MSVC 19.34): ASan executables fail to start with `0xc0000142` (DLL initialization failed). | `windows-asan` tests cannot run on old VS installs. | Update Visual Studio; verified working on 17.14 (MSVC 19.44), and in CI. Requirement documented as VS 2022 17.10+. | Documentation only. |
| KI-008 | ~~clang-tidy versions differ between CI jobs: 18 on Linux, 19 on Windows.~~ **Mostly closed 2026-10-18:** Linux CI now runs clang-tidy 19.1.0 pinned through uv (same check set as VS's 19.1.5). Remaining gap: files that only compile on Windows (`src/platform/windows/*.cpp`) are checked only by the Windows job. | A finding in Windows-only code still fails only the Windows `clang-tidy` job. | Run `.\scripts\dev.ps1 tidy` locally before pushing. Linux side reproduces locally with `uv run clang-tidy` (any OS). History of Windows-only findings: designated initializers, static-constant naming, ignored return values (M1.1/M1.2); MSVC CRT parameter names, exceptions treated as disabled (M1.9); `modernize-use-ranges`, `bugprone-suspicious-stringview-data-usage` (M2.1/M2.2). | Revisit if the pinned and bundled versions drift apart (bump with `uv lock --upgrade-package clang-tidy`). |
| KI-009 | The allocation test (`tests/alloc`) replaces the global `operator new`/`delete`; it is not built under TSan (its runtime defines them too: duplicate symbols) or MSVC ASan (its runtime hooks them). | Zero-allocation behaviour is not re-checked in those two configurations. | It runs in every other configuration (GCC, Clang, Linux ASan/UBSan, Release, coverage, MSVC Debug/Release, clang-cl); the ring code is identical in all of them. | Permanent tool limitation. |
| KI-010 | Shared-memory lifetime differs by OS: a POSIX segment outlives a crashed creator (stale name in `/dev/shm`); a Windows mapping stays openable while any process holds a handle, even after its creator exited. | Without care, a new creator could fail with AlreadyExists (POSIX), or a late opener could attach to a dead publisher's segment (Windows). | fastbus semantics "creator owns lifetime" (PRD_shm_transport §3.1): the creator unlinks on destroy; stale names are removed explicitly (`SharedMemory::remove`, `fbclean` in M2.9) after checking the creator's identity (pid + start time); the M2.3 header's `closing` state makes Windows behave the same above the platform layer. Pinned by a per-OS test. | Permanent OS difference; handled by design. |
| KI-011 | `SharedMemory::create` commits all pages up front (`posix_fallocate` / `SEC_COMMIT`). | A large segment uses its full RAM/pagefile budget at creation, even if never touched. | Deliberate: a size-limited `/dev/shm` (containers, CI) then fails at creation with OutOfMemory instead of a SIGBUS later in the hot path. Segment sizes are configured per topic (M3). | Revisit only if lazy commit is ever needed. |
| KI-005 | TSan instruments one process only, so it cannot observe races between processes on shared memory. | From M2, races between a publisher and a subscriber process on the same ring are invisible to TSan. | The ring is one header-only implementation (`SpscRingView`) that is identical in-process and in shm, and it holds no pointers; its ordering is proven in `docs/memory-ordering.md` and checked in-process with threads under TSan (unit + 18 stress cases, M1.7/M1.8). M2 adds cross-process invariant/stress tests (order, no loss, no torn payloads) that run without TSan. | Permanent tool limitation (re-checked M1.8). |
