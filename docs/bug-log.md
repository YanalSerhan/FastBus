# Bug log

Every genuine bug hit during development — raw material for M8. Do not skip entries in M1–M7.

| Date | ID | Symptom | How found | Root cause | Fix commit |
|---|---|---|---|---|---|
| 2026-10-16 | BL-001 | `windows-clangcl` preset would fail on the first compile: `argument unused during compilation: '/external:anglebrackets'` | Compiled a probe file with clang-cl and the exact flag set before the preset was ever run | MSVC-only `/external:*` flags were applied to clang-cl, and `/WX` turned the unused-argument warning into an error | `fix(build): give clang-cl its own warning flags` |
| 2026-10-16 | BL-002 | All 5 Windows CI jobs failed at "Toolchain check" with `exit code 1` although `dev.ps1 doctor` printed "all required tools found" | CI run #3; reproduced locally by running the script inside GitHub's pwsh wrapper (`... ; exit $LASTEXITCODE`) | `doctor` ends with `git config --get core.longpaths`, which exits 1 when the key is unset; the script never exited explicitly, so the stale `$LASTEXITCODE` became the step result | `fix(scripts): exit dev.ps1 explicitly so stale native exit codes don't fail CI` |
| 2026-10-16 | BL-003 | Windows clang-cl and clang-tidy CI jobs failed at configure: `clang: error: no such file or directory: '/DWIN32'` while checking the C compiler | CI log of `windows (clang-cl)` (configure step, called from GoogleTest's `project()`) | The project is C++-only, but GoogleTest enables C. The preset set only `CMAKE_CXX_COMPILER=clang-cl`, so CMake picked GNU-style `clang.exe` for C and fed it MSVC-style flags | `fix(build): use clang-cl for C as well in the clang-cl presets` |
| 2026-10-16 | BL-004 | `windows-tidy` used `C:/Program Files/LLVM/bin/clang-tidy.exe` although dev.ps1 put Visual Studio's clang-tidy first on PATH | Same CI log (`fastbus: clang-tidy enabled (...)` line) | `find_program(... HINTS ...)` searches HINTS before PATH | Same commit; PATH search first, install folders only as fallback |
| 2026-10-16 | BL-005 | Local `windows-asan` tests failed to start: `Exit code 0xc0000142` during gtest discovery, while the same job passed in CI | Owner's `dev.ps1 check` run | Visual Studio 2022 17.4 (MSVC 19.34) ASan runtime; not a code bug | No code change: updated VS to 17.14 (KI-007) |
| 2026-10-17 | BL-006 | `coverage` target failed: gcovr `NegativeHits ... thread_owner.hpp:36 Got negative hit value` | First coverage report after the multi-threaded ring tests were added (M1.6) | gcov counters are plain non-atomic increments by default; two threads running the same code at once (the concurrent `size_approx` test) corrupt them | `fix(cmake): build coverage with -fprofile-update=atomic` |
